## 2. Provider Architecture

```text
PaymentIntent
  -> PaymentService
      -> provider router
          -> PaystackAdapter      # primary
          -> FlutterwaveAdapter   # fallback
      -> PaymentRepository
      -> ProviderEvent inbox
      -> verification/reconciliation
```

Provider DTOs never become CartNest order/payment DTOs.

## 3. Current Provider API Baseline

P7 was rechecked against current official provider documentation on 5 September 2026.

### Paystack

The adapter uses the server-side transaction API:

```text
POST /transaction/initialize
GET  /transaction/verify/:reference
```

Important provider behavior used by CartNest:

- amount is sent in currency subunits (kobo for NGN);
- secret key stays server-side;
- provider reference is generated by CartNest;
- `x-paystack-signature` is verified using HMAC-SHA512;
- transaction verification is performed before CartNest gives fulfillment value.

Official references:

- https://paystack.com/docs/api/transaction/
- https://paystack.com/docs/payments/webhooks/
- https://paystack.com/docs/payments/multi-split-payments/

### Flutterwave

P7 deliberately implements one coherent **Flutterwave v3 Standard** surface rather than mixing newer charge API conventions with v3 settlement/split conventions:

```text
POST /v3/payments
GET  /v3/transactions/verify_by_reference?tx_ref=...
```

Important provider behavior used by CartNest:

- amount is sent in major currency units, so the adapter performs exact integer-minor-unit conversion;
- the hosted checkout link is returned to the caller;
- `flutterwave-signature` is verified as Base64 HMAC-SHA256 over the raw body using the configured secret hash;
- server verification must match status, reference, currency and expected amount before value is granted.

Official references:

- https://developer.flutterwave.com/v3.0.0/reference/checkout
- https://developer.flutterwave.com/v3.0/reference/verify-transaction-with-tx_ref
- https://developer.flutterwave.com/docs/webhooks
- https://developer.flutterwave.com/v3.0/docs/split-payments

Provider APIs remain external dependencies and must be revalidated in sandbox before production release.

## 4. Payment Initialization API

P7 adds:

```text
POST /api/v1/payment-intents/:paymentIntentId/initialize
GET  /api/v1/payment-intents/:paymentIntentId
POST /api/v1/payment-intents/:paymentIntentId/reconcile
```

Initialization requires:

```text
Idempotency-Key: <caller generated key>
```

Optional buyer-facing channel choices currently include:

```text
card
bank
ussd
bank_transfer
```

Provider selection is not exposed to the buyer.

A hosted-provider payment currently requires the CartNest user to have an email address because both selected hosted checkout flows require customer email.

## 5. Safe Provider Routing

The implemented routing invariant is:

```text
Paystack initialize
  |
  +-- initialized --------------------> return hosted checkout
  |
  +-- definite non-charge rejection --> Flutterwave may be attempted
  |
  +-- timeout / network unknown ------> PROCESSING; fallback blocked
```

A network timeout after request dispatch is never interpreted as proof that no provider transaction exists.

An ambiguous Paystack result therefore produces:

```text
PAYMENT_OUTCOME_UNKNOWN
```

and the attempt remains reconciliation-required. CartNest will not automatically create a Flutterwave charge in that state.

## 6. Payment Initialization Idempotency

Initialization uses the existing `IdempotencyRecord` model with an operation scoped to the PaymentIntent:

```text
principalId = authenticated buyer
operation   = payment.initialize:<paymentIntentId>
key         = Idempotency-Key
fingerprint = SHA-256(paymentIntentId + channel)
```

Behavior:

```text
same key + same request + completed
  -> replay stored initialization response

same key + changed request
  -> 409 IDEMPOTENCY_KEY_REUSED

same key + unresolved provider outcome
  -> PAYMENT_INITIALIZATION_IN_PROGRESS

new key while another provider attempt is active
  -> PAYMENT_ATTEMPT_ACTIVE
```

This prevents an impatient client from creating a second charge while the first provider outcome is unresolved.

## 7. PaymentAttempt State

P7 uses the existing provider-neutral state model:

```text
PENDING
  -> REQUIRES_ACTION   hosted checkout initialized
  -> PROCESSING        provider outcome ambiguous/pending
  -> FAILED            provider proves non-success
  -> SUCCEEDED         server verification proves success
  -> CANCELLED         superseded non-final attempt after another attempt succeeds
```

`providerReference` is treated as the provider transaction correlation key. Provider numeric transaction IDs are stored as strings at the API/domain boundary so large provider identifiers are not truncated by JavaScript number semantics.

## 8. Webhook Security

P7 adds:

```text
POST /api/v1/webhooks/paystack
POST /api/v1/webhooks/flutterwave
```

The API uses `fastify-raw-body` with route-scoped raw-body retention.

Webhook processing is:

```text
raw HTTP body
  -> verify provider signature
  -> normalize provider event identity/reference
  -> ProviderEvent inbox
  -> dedupe
  -> find known PaymentAttempt
  -> re-query provider verification API
  -> exact CartNest invariant checks
  -> idempotent financial/state transition
```

A browser redirect or a webhook payload alone does not mark an order paid.

## 9. ProviderEvent Deduplication

When the provider supplies an external event ID, the existing provider/event uniqueness is used.

When it does not, P7 uses:

```text
SHA-256(raw webhook body)
```

as the fallback fingerprint.

`required-constraints.sql` now includes a partial unique PostgreSQL index on `(provider, fingerprint)` for events without an external event ID, making the fallback deduplication race-safe.

Duplicate verified events do not repeat inventory, order, or allocation effects.

## 10. Verification Gate

A successful provider status is insufficient by itself.

CartNest requires exact agreement on:

```text
provider reference
expected PaymentIntent amount
expected currency
provider success status
```

CartNest intentionally uses **exact amount matching** even where generic provider documentation allows overpayment acceptance.

If a provider reports success but amount, currency, or reference does not match, CartNest records a mismatch/reconciliation condition and does not grant order fulfillment value.

## 11. Successful Payment Transaction

After verification proves payment success, P7 performs the internal transition transactionally and idempotently.

Normal path:

```text
PaymentAttempt -> SUCCEEDED
PaymentIntent  -> SUCCEEDED
InventoryReservation HELD -> COMMITTED
InventoryItem.onHand  -= quantity
InventoryItem.reserved -= quantity
Order.paymentStatus -> SUCCEEDED
Order.status        -> PAID
VendorOrders PENDING -> ACCEPTED
PaymentAllocations created
AuditLog written
payment.succeeded OutboxEvent written
```

The PaymentIntent transition is claimed atomically so two simultaneous webhook/reconciliation paths cannot both apply the financial effects.

Any remaining non-final attempts are cancelled after a verified attempt succeeds.

## 12. Late Payment / Reservation Loss

A provider can report payment success after a reservation has expired, been released, or become unavailable.

CartNest does not invent inventory in that case.

Instead:

```text
PaymentIntent  -> SUCCEEDED
Order.paymentStatus -> SUCCEEDED
Order fulfillment status does NOT advance to PAID
stock is not committed
payment.manual_review_required outbox event is emitted
```

This preserves financial truth while blocking fulfillment until an operator/refund policy resolves the inconsistency.

## 13. Commission Resolution

The approved product decision says commission must support a platform default plus vendor/category overrides. The previously unspecified rule precedence is now defined by the P7 implementation baseline as:

```text
1. vendor + category rule
2. vendor-only rule
3. category-only rule
4. platform default rule
```

Within equal specificity:

```text
higher priority wins
then newest rule wins
```

Commission is calculated per line in integer minor units.

If one VendorOrder contains products from categories with different rules, `commissionAmountMinor` is the exact sum of line commissions and `commissionRateBps` is stored as the effective weighted VendorOrder rate.

No binary floating-point money arithmetic is used.

Production configuration must include an intentional platform default commission rule. Development currently permits a zero fallback so P7 source work can continue before seeding/configuration is finalized.

## 14. Gateway Fee Policy and PaymentAllocation

The approved MVP policy says the vendor bears gateway transaction fees.

P7 reads the provider-reported fee where available and allocates it proportionally across represented VendorOrders.

For each VendorOrder, the accounting components are:

```text
VENDOR_NET
  = item subtotal
  - discount
  - platform commission
  - allocated gateway fee

PLATFORM_COMMISSION
GATEWAY_FEE
DELIVERY
TAX
```

The total of all positive allocation rows must reconcile exactly to the captured PaymentIntent amount.

If the provider fee would make a vendor net negative or allocation arithmetic does not reconcile exactly, CartNest does not silently write incorrect allocations. Payment financial truth remains successful but a `payment.manual_review_required` event is emitted.

## 15. Collection-Time Provider Splits

P3 already models approved provider/subaccount records and the provider boundary permits split instructions.

However, CartNest's approved settlement policy is **delivery-gated with a scheduled release target**, while ordinary provider collection-time split payments can settle vendor shares independently of CartNest's delivery gate.

Therefore:

```text
PAYMENT_COLLECTION_SPLITS_ENABLED=false
```

is the safe default and P7 does not enable provider collection-time split settlement automatically.

Subaccount/split activation requires an explicit finance/operations decision showing that the chosen provider configuration preserves the approved delivery-gated settlement behavior. Internal `PaymentAllocation` remains authoritative regardless of provider movement of funds.

## 16. Reconciliation

`PaymentService.reconcilePending()` now provides the provider-neutral reconciliation primitive.

It scans non-final attempts older than the short reconciliation threshold and performs server-side verification.

The authenticated buyer can also request reconciliation for their own PaymentIntent:

```text
POST /api/v1/payment-intents/:paymentIntentId/reconcile
```

The remaining infrastructure task is wiring `reconcilePending()` into the approved BullMQ/worker scheduler. That wiring is not falsely marked complete in P7.
