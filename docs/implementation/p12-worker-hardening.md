# FP12 Durable Worker Hardening Checkpoint

**Phase:** FP12

**Updated:** 7 September 2026

## Implemented source baseline

The worker now contains a PostgreSQL transactional-outbox dispatcher, BullMQ queue registry, notification consumer, reservation-expiry maintenance consumer, scheduled maintenance enqueueing, controlled failed-outbox replay, graceful shutdown, and worker health accounting.

The dispatcher uses `FOR UPDATE SKIP LOCKED`, bounded publish attempts, stale lease reclamation, exact lease compare-and-set finalization, event-version validation, and durable event IDs as BullMQ job IDs.

Notification materialization is idempotent through existing notification `dedupeKey` uniqueness/upsert behavior. Missing referenced aggregates now fail instead of returning successful zero-work results, preventing silent loss of required notification work.

## Redis-loss reconstruction

A reviewed recovery command is now exposed:

```bash
WORKER_REDIS_RECOVERY_SINCE=<ISO timestamp> \
WORKER_REDIS_RECOVERY_CONFIRM=REBUILD_IDEMPOTENT_NOTIFICATION_JOBS \
pnpm --filter @cartnest/worker outbox:recover
```

The command:

- reads `PUBLISHED` version-1 outbox events from PostgreSQL;
- rebuilds only currently subscribed notification jobs;
- reuses the original outbox event ID as the BullMQ job ID;
- relies on notification dedupe keys for database-level idempotency;
- refuses windows larger than 10,000 events so recovery cannot silently truncate evidence;
- writes a SYSTEM audit record with the recovery window and aggregate counts;
- deliberately does not rebuild future payment/refund execution jobs.

This recovery path is intentionally narrower than general event replay. Financial execution must remain under dedicated reconciliation/replay controls.

## Reproducibility blocker

The repository still has no committed root `pnpm-lock.yaml`. BullMQ is declared as `6.3.4`, but a real lockfile and transitive dependency graph must be generated by pnpm in a trusted network-enabled environment. The lockfile must not be fabricated manually.

Until that exists, frozen-lockfile CI/Docker installation is expected to fail.

## Runtime evidence still required

No runtime pass is claimed yet. Required evidence includes:

- worker dependency installation from a committed lockfile;
- TypeScript/lint/test/build execution;
- PostgreSQL outbox concurrency tests;
- Redis/BullMQ integration execution;
- crash-after-enqueue recovery;
- stale lease reclaim behavior;
- reservation expiry idempotency and stock invariants;
- failed/dead-letter visibility;
- controlled replay;
- Redis-loss reconstruction using the recovery command;
- graceful shutdown while jobs are active;
- queue latency/failure observability.

External EMAIL/SMS delivery, payment reconciliation, GIGL tracking sync, and additional maintenance jobs remain separate source/runtime gaps.
